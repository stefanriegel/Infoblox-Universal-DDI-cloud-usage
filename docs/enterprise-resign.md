# Enterprise Re-Signing Guide for setup_venv.ps1

## Overview

The distributed `setup_venv.ps1` is signed with a self-signed certificate generated by the CI
pipeline (`CN=Infoblox UDDI Estimator`). Self-signed certificates are not trusted by default on
machines outside the original domain, and enterprise IT departments typically require scripts to be
signed with a certificate from their own internal CA or a trusted commercial CA.

This guide covers two paths:

1. **Enterprise re-signing** -- sign the script with your organization's certificate (recommended
   for domain-joined machines)
2. **Importing the self-signed certificate** -- trust the distributed cert on individual machines
   (suitable for lab/demo environments without an internal CA)

---

## Path 1: Enterprise Re-Signing

### Prerequisites

- A code signing certificate issued by your enterprise's internal CA (or a trusted commercial CA)
- The certificate must have the `Code Signing` enhanced key usage (EKU)
- The certificate must be installed in `Cert:\CurrentUser\My` on the machine where you sign

### Re-Signing Steps

```powershell
# 1. List available code signing certificates to find yours
Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert | Select-Object Subject, Thumbprint, NotAfter

# 2. Select your enterprise certificate (replace YourCompany with your org name or CN)
$cert = Get-ChildItem Cert:\CurrentUser\My -CodeSigningCert |
    Where-Object { $_.Subject -like "*YourCompany*" }

# 3. Confirm the correct certificate is selected
Write-Host "Signing with: $($cert.Subject) (expires $($cert.NotAfter))"

# 4. Sign the script
$result = Set-AuthenticodeSignature -FilePath setup_venv.ps1 -Certificate $cert
if ($result.Status -ne 'Valid') {
    throw "Signing failed: $($result.StatusMessage)"
}
Write-Host "Script signed successfully: $($result.Status)"

# 5. Verify the signature
Get-AuthenticodeSignature -FilePath setup_venv.ps1 | Select-Object Status, SignerCertificate
```

### Distributing the Re-Signed Script

Place the re-signed `setup_venv.ps1` in the tool directory alongside the other files. On
domain-joined machines where the enterprise CA is already trusted (as it should be by group
policy), users can run the script without any additional certificate import steps.

---

## Path 2: Importing the Self-Signed Certificate

Use this approach in environments without an enterprise CA -- for example, standalone lab machines
or customer demos where you control the target machine.

```powershell
# Requires an elevated (Run as Administrator) PowerShell session

# Import cert.cer (distributed alongside setup_venv.ps1) into the trusted root store
Import-Certificate -FilePath .\cert.cer -CertStoreLocation Cert:\LocalMachine\Root

# Verify it was imported
Get-ChildItem Cert:\LocalMachine\Root | Where-Object { $_.Subject -like "*UDDI Estimator*" }
```

After importing, the script signature will be trusted on that machine. The import is a one-time
step per machine.

---

## Troubleshooting

**"The signature of the certificate cannot be verified"**
The signing certificate is not in a trusted store. Either import `cert.cer` to
`Cert:\LocalMachine\Root` (Path 2 above) or re-sign with an enterprise certificate (Path 1).

**"Script cannot be loaded because running scripts is disabled on this system"**
The PowerShell execution policy is `Restricted`. Run the following to allow signed scripts:
```powershell
Set-ExecutionPolicy RemoteSigned -Scope CurrentUser
```
If group policy enforces `Restricted`, contact your IT administrator -- policy-enforced execution
policy cannot be overridden by the user.

**"Cannot find a certificate that can be used for authentication"**
No code signing certificate is installed for your user. Request one from your internal CA, or use
the self-signed `cert.cer` import approach for non-production environments.

**GPO-enforced AllSigned or Restricted policy**
If your organization enforces `AllSigned` execution policy via GPO, the script must be signed with
a certificate from a CA trusted by the machine. Re-sign with your enterprise certificate (Path 1)
and ensure the CA is in `Cert:\LocalMachine\Root` or `Cert:\LocalMachine\CA`.
